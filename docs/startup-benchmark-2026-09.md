# 启动基准：2026 年 9 月

本机 10,000 首曲库的可操作时间中位数由 **3,729.86 ms 降至 626.97 ms，降低 83.2%**；1,000 首降低 28.0%，空曲库降低 1.3%。大曲库收益主要来自分页摘要查询、减少主线程工作以及减少首屏加载和渲染内容。空曲库及 1,000 首尚未达到降低 30% 的目标；完整后台校验在小曲库下会更晚完成。

## 硬件与测量方法

- Apple M4，16 GB 内存，macOS / Darwin 25.6.0，原生 arm64。
- 同一台机器、同一套 Electron 43.1.1 和桌面工具，运行优化前后生产构建；由开发 Electron 加载，未测量签名安装包。
- 曲库规模为 0、1,000、10,000 首。每首有 6 个分轨元数据，每 5 首有 1 个已完成吉他细分任务；三分之一有练习时间。音频文件和封面未模拟，Python 环境与模型未安装。
- 使用独立临时目录，路径含中文、空格和括号；不读取或修改用户曲库。数据库迁移预先应用，排除首次迁移耗时。
- 每个版本、每个规模先预热 1 次，再测量 10 次；前后版本交错运行，共启动 66 次，60 次计入统计。测量期间暂停其他重负载测试。
- 从外部进程发起 Electron 启动的单调时钟开始，记录主进程标准输出收到阶段事件的时间。中位数取第 5、6 个排序样本的平均值；P95 使用最近秩算法，10 个样本时等于最大值。

阶段定义：

| 阶段 | 完成条件 |
| --- | --- |
| 窗口可见 | `ready-to-show` 后调用 `window.show()`；当前版本此时显示可操作的启动界面 |
| 曲库可操作 | 首次曲库查询成功、React 提交后，再经过两个动画帧 |
| 后台就绪 | 媒体工具完整性校验与 `runtime.detect()` 都已结束；空环境下不代表分轨模型已安装 |

前后版本使用相同事件和可操作判定。当前版本将启动界面与 React 主应用分开：窗口可见不代表曲库已可操作；后者仍需真实查询成功及 React 提交。优化前媒体校验在主线程同步完成，优化后异步执行，因此后台就绪和窗口可见的先后顺序可以不同。

## 结果

所有时间单位均为毫秒。

| 曲目数 | 阶段 | 优化前中位数 | 优化后中位数 | 优化前 P95 | 优化后 P95 |
| ---: | --- | ---: | ---: | ---: | ---: |
| 0 | 窗口可见 | 504.73 | 449.15 | 547.64 | 482.26 |
| 0 | 曲库可操作 | 537.90 | 531.13 | 586.88 | 566.42 |
| 0 | 后台就绪 | 415.21 | 649.44 | 455.85 | 708.89 |
| 1,000 | 窗口可见 | 478.94 | 453.23 | 497.79 | 476.47 |
| 1,000 | 曲库可操作 | 769.74 | 554.17 | 792.87 | 583.43 |
| 1,000 | 后台就绪 | 429.83 | 686.45 | 452.27 | 700.89 |
| 10,000 | 窗口可见 | 1,135.27 | 460.65 | 1,151.78 | 472.49 |
| 10,000 | 曲库可操作 | 3,729.86 | 626.97 | 3,865.43 | 634.55 |
| 10,000 | 后台就绪 | 1,066.31 | 763.23 | 1,085.23 | 794.40 |

空曲库和 1,000 首曲库的后台就绪中位数分别增加 234.23 ms、256.62 ms。初始化顺序改为先显示启动界面，再准备数据库及并行启动界面代码；媒体完整性校验继续异步执行，使用工具前仍等待验证通过。10,000 首曲库的窗口可见中位数降低约 59.4%。

完整运行记录、预热样本、构建主入口 SHA-256 和统计结果见 [原始 JSON](./benchmarks/startup-2026-09.json)。其中已去除本机绝对目录。

## 重现

本次优化前源码快照保存在工作区的 `.codex-tmp/performance-baseline`，包含与当前版本等价的三个阶段埋点；它不属于 Git 跟踪文件。使用 Node.js 24、已安装的项目依赖和已校验桌面工具，在该快照仍可用时执行：

```bash
(cd .codex-tmp/performance-baseline && pnpm exec electron-vite build)
pnpm build
node scripts/benchmark-startup.mjs --baseline=.codex-tmp/performance-baseline --runs=10 --sizes=0,1000,10000 --output=.codex-tmp/startup-benchmark-rerun.json
```

仅测量当前版本可使用：

```bash
node scripts/benchmark-startup.mjs --variant=current --runs=10 --sizes=0,1000,10000
```

比较其他版本时，先准备独立的优化前源码和构建产物，加入相同的 `BAND_BUDDY_METRIC` 埋点，再通过 `--baseline=<目录>` 指定。脚本检查埋点是否存在，自动建立独立数据库，并在阶段缺失或启动失败时终止；不要在测量期间重建产物。

## 适用范围与回归防护

这是热文件缓存下的一台 Apple Silicon 设备结果，不能代表系统冷启动、首次安装/迁移、Windows、Intel Mac、低内存设备、已安装大型模型或真实音频播放延迟。每组只有 10 个样本，P95 用于观察较慢样本，不能代替更大规模尾延迟统计。

真实启动预跑发现并修复了主进程依赖被错误打包、输出格式覆盖以及沙箱预加载共享模块拆分导致的失败。`pnpm build` 末尾现在执行 `verify:built-runtime`，检查两个预加载文件独立输出、原生主进程依赖保持外置、分析与数据库准备 worker 文件存在。这些静态检查与真实启动测试共同用于回归防护。
